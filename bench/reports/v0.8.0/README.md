# Benchmark reports: llm-mini-infer against vLLM v0.33.0 and SGLang v0.5.23

This folder holds a comparison of three serving engines on one GPU, with every raw report and the commands that produced them. `summary.md` and `summary.json` hold the numbers; `summarize.py` derives them from the files here (`python3 bench/reports/v0.8.0/summarize.py`). `bench/reports/check.py` checks the folder for private data.

**The author of llm-mini-infer wrote this harness.** llm-mini-infer is built for this GPU and these two model families; vLLM and SGLang are general-purpose engines, run here with their documented recipe flags and the settings held equal below.

## What ran

- **Engines:** llm-mini-infer at two measured commits, each from the GPU tests' image of that commit: `2b321dbd00013dcfe7f5f72b932fe7748aa2c4d0` (`sha256:ad69be85478c6d92b35740e57192dde61aef86d649578a16e4b7b02cc93c6b8b`) for hosts `p1` and `p2`, and a second, `bfc310dfcf273907f5af0a071a7aa77c9ed55ff4` (`sha256:4fb1da6f0a254578173632717ec8b69b467d72a4a681b98a6c9fd2afba562d11`), for host `p3`, which changes the benchmark's own code only (`bench/`: the driver's fixes and the arms `p3` ran). Both commits are from the project's history before its first public commit, and their GPU tests' images were not published; the manifests carry the same ids and digests. Their serving code (`llm_mini_infer/`, `deploy/`, `pyproject.toml`, `uv.lock`) is this tree's, apart from comments, docstrings, version numbers, pyproject's authors, URLs and ruff exclude, and one test marker's description. vLLM v0.33.0 and SGLang v0.5.23 from their CUDA 13 wheels, each in a venv of its own on the same image, pinned to the versions in their vendor images (`vllm/vllm-openai:v0.33.0`, `lmsysorg/sglang:v0.5.23-cu130-runtime`). `freeze-diff.txt` compares each venv with its image: every package both hold is at the image's version but the engine itself (a wheel built inside vLLM's image, SGLang editable in its image); the images hold more packages, which these arms served every request without. `vendor-images.json` holds the images' digests, sizes and the vendor pods' own reads.
- **Models:** `RedHatAI/gemma-4-31B-it-FP8-block` with `google/gemma-4-31B-it-assistant` (draft count k = 5), and `Qwen/Qwen3.8-27B-FP8` with its MTP layer (k = 3). The manifests record each repository's revision.
- **GPU:** one NVIDIA RTX PRO 6000 Blackwell Server Edition at 600 W, driver 595.91.07, CUDA 13.2, per host. Hosts: `p1` ran Gemma's smoke checks and family A1; `p2` ran Gemma's A2, C, D and B and every Qwen family of llm-mini-infer and vLLM; `p3` ran the second commit's arms: vLLM's batch invariance without DeepGEMM (family C), the cost of batch invariance on one host (family I), SGLang on Qwen3.8 (A1, C, D) and Qwen3.8's A1 for the other two engines, so that every Qwen3.8 A1 row is from one host (`p2`'s A1 for them stays published: Qwen3.8's bound was fixed from it); `q-vllm` and `q-sglang` ran the vendor-image check (family Q). Each table row in `summary.md` names its host. The GPU control (`control/`) measures a host's GPU alone: `p2` and `p3` at their start, middle and end, `p1` at its start (it was replaced after A1), the vendor pods at their start and end; `p2`'s and `p3`'s GPUs gave 2 to 3% more bf16 and fp8 throughput than `p1`'s at their start. `p1`'s CPU quota was 27.2 cores, `p2`'s and `p3`'s 13.6, on the same CPU model (the manifests' `host`).
- **Clients:** `bench/load/run.py` on the same host over the loopback interface, streaming, temperature 0, thinking off in every request, seed 0.

## The arms

| | llm-mini-infer | vLLM v0.33.0 | SGLang v0.5.23 |
|---|---|---|---|
| held equal | context 8,184; 64 sequences (SGLang on Qwen3.8: 48, below); KV in the model's dtype; prefix caching on; llguidance with compact JSON; the same drafter and k; each model's default image budget (prompt tokens checked equal per request); no reasoning parser | the same | the same |
| batch invariance by default | on (its default at this context) | off | off |
| batch invariance on | default | `VLLM_BATCH_INVARIANT=1` | `--enable-deterministic-inference` |
| memory budget | 0.9 | `--gpu-memory-utilization 0.9` | its computed static fraction |
| per-step tokens | 2,048 (default) | 8,192 (default) | 8,192 (default) |
| FP8 GEMM | CUTLASS | DeepGEMM (Gemma 4, its default); CUTLASS with `VLLM_USE_DEEP_GEMM=0` (the arm `vllm-bi-nodg`); its CUTLASS path (Qwen3.8), as its startup log selects | `auto` (v0.5.23 logs no selection; its source resolves `auto` to CUTLASS on this GPU) |
| attention | FlashInfer | TRITON_ATTN (Gemma 4, forced by vLLM); FLASH_ATTN (Qwen3.8) | triton (Gemma 4); flashinfer (Qwen3.8; triton with deterministic inference, which also enters its stability and cost rows) |

KV capacity is not matched; each manifest's `resolved` records it (llm-mini-infer's Gemma 4 figure counts a KV arena shared by window and full pages, a different quantity from the others'). `commands.sh` holds every server command and the driver's commands, the vendor-image check's included.

## The families

| family | what | loads |
|---|---|---|
| smoke | every arm's start, checked before timing: a cached prefix, valid compact JSON, no reasoning, verify steps, prompt tokens | none |
| A1 | latency and throughput at the same k | c=1: 150 scene, 80 chat requests; c=16 and c=64, 60 s each, both workloads |
| A2 | the highest Poisson rate within the latency bound | scene; from 0.4x to 1.0x the engine's A1 c=64 rate, resolution 0.1x, one confirmation |
| C | answer stability, batch invariance off and on | two passes on two fresh servers, c=16, 500 scene requests; vLLM's invariance on Gemma 4 twice, with DeepGEMM (`vllm-bi`, `p2`) and without (`vllm-bi-nodg`, `p3`); the non-default mode's c=64 loads (both workloads) on pass 1's server |
| I | the cost of batch invariance on one host (Gemma 4) | each engine in both modes on fresh servers on `p3`: c=64 scene and chat; vLLM's invariant arm is `vllm-bi-nodg`, which also turns DeepGEMM off: its ratio is the cost of the configuration in which its invariance holds, not of the switch alone |
| D, S | cold and warm start; structured-output validity | a cold start (the engine's cache roots emptied; the weights' pages advised out of the page cache, their residency not measured; llm-mini-infer's prebuilt kernels are part of its image), a warm restart, then `bench/structured/validity.py` on the benign corpus, with a liveness check (not for SGLang: below); llm-mini-infer's grammar compile cost (`bench/structured/grammar_cost.py`) |
| B | vLLM's own draft counts | Gemma 4 k = 1 (its code default) and k = 4 (its recipe); Qwen3.8 k = 1; c=1 (100 scene) and c=64 scene |
| Q | the venvs against the vendors' images | Gemma 4: c=1 (100 scene) and c=64 scene, on each vendor image |

Scene is the synthetic image workload with a strict JSON schema (`llm_mini_infer.synthetic`); chat has 1,024-token prompts and 256-token replies under `ignore_eos`, so every engine decodes the same tokens. Scene replies are each engine's own answers and differ in length: compare scene latency and throughput beside the reply-token columns. Only the count-bounded loads and the rate search send 20 warm-up requests first (the manifests' `client`).

## Definitions

- **The latency bound** (per model and workload, fixed after A1 and before any rate search): e2e p99 at most 2x the median, across the engines that ran, of their A1 c=1 e2e p50, with zero drops and zero failures (`bounds/`).
- **A probe passes** when no request failed or was dropped, the served rate is at least 0.95 of the offered rate, and its e2e p99 is under the bound.
- **Stability:** the share of answers identical between two passes on two fresh servers, over the requests both passes answered: the same content (a SHA-256 digest), the same token count and the same finish reason.
- **Tokens per verify step:** the completion tokens after the first, over the server's verify steps, across a whole load (each load's `spec`). llm-mini-infer also delivers tokens no verify step makes (a grammar's forced tokens), so compare acceptance on the chat workload.
- **Start-up:** the time from the process's start to its first answer to one fixed request (`first_answer_s`), beside the time to its readiness path's 200 (`ready_s`).

## Deviations from the method, and what did not run

- **llm-mini-infer's configuration file.** At the first measured commit, `bench/engines/arms.py` starts llm-mini-infer without `--config`, so it would serve without the image's configuration (llguidance's compact JSON, seed 0). Every llm-mini-infer arm on `p1` and `p2` ran with `--config $LLM_MINI_INFER_CONFIG` added through the driver's `--add-arg`, as the image's entrypoint passes it; each manifest names it. At the second commit (`p3`) the arm's own command names it, as it does in this tree.
- **SGLang on Qwen3.8 runs 48 sequences, not 64.** At 64 its hybrid cache keeps 5 SSM states per request (3, plus 2 for its extra-buffer radix strategy), in float32 as Qwen3.8 declares them: about 49 GB, against the about 41 GB its static memory fraction leaves after the target model and its MTP layer. On `p2` it did not start, nor did two corrected starts: without `--enable-linear-replayssm-spec`, and with `--mem-fraction-static 0.85` (`p2`'s manifests hold the arm as designed, `qwen/A1/sglang`, and the second try, `qwen/smoke/sglang`; the first try's log is not published). On `p3` it ran with `--max-running-requests 48` and `--max-mamba-cache-size 240`, 48 being SGLang's own value under speculative decoding; each of its manifests names the deviation. At 64 in flight (A1's c=64 loads, the cost of invariance) the client keeps 64 requests open and 16 of them queue in SGLang's server, so its c=64 rows are not at the others' concurrency. Qwen3.8's bound stays the median over llm-mini-infer and vLLM, fixed before SGLang ran, and SGLang has no A2 or B row on Qwen3.8.
- **vLLM's batch invariance refuses Qwen3.8** ("VLLM batch_invariant mode is not supported for GDN_ATTN."): recorded as unsupported.
- **SGLang has no structured-output row.** Its run on Gemma 4 first stopped the server: its speculative-sampling kernel, built at the first request above temperature 0, includes `curand.h`, which the GPU tests' image lacks and SGLang's own CUDA-devel image has. That run's cold start also reused SGLang's JIT kernels, which v0.5.23 keeps in `~/.cache/sglang/jit`, outside `SGLANG_CACHE_DIR`. The published D unit is a second run, with the cuRAND headers copied from SGLang's own venv into the CUDA include directory and that folder emptied before the cold start; its start-up times stand, its validity report is left out of this folder (its manifest says so). On `p3` the venv step copies the headers before any run and every SGLang manifest says so, the cold start empties `~/.cache/sglang` (the second commit's cache roots), and SGLang's Qwen3.8 D unit ran its starts only (`--skip-validity`).
- **The vendor-image check:** vLLM's c=1 TPOT on `p1` was 1.3% under its image's after the GPU control's host ratio; SGLang's 5.0% under (faster than its image), just past the 5% bound fixed before the run. The comparison went on with the venvs; the venvs and their freezes are what this folder measures.
- **Three hosts.** `p1` was replaced by `p2` after Gemma's A1, when the vendor-image check's result was known; Gemma's A1 is `p1`'s. `p3` ran the second commit's arms later, on the same GPU, driver, CPU model and CPU quota as `p2` (its start control within 0.5% of `p2`'s). The cost of invariance compares runs on one host only: fresh servers on `p3` for Gemma 4 (family I), and for Qwen3.8 each engine's A1 c=64 loads with its other mode's c=64 loads in C on the same host (`p2` for llm-mini-infer, `p3` for SGLang); those servers had run other loads first.
- **Qwen3.8's latency bound** (667.6 ms) is below both engines' c=1 e2e p99 on its scene workload, whose answers are short with a long tail: neither has a rate within it. Its scene answers are few: every engine gave 13–20 distinct answers to the 500 stability requests, most of them one short answer (308–411 requests a pass), so Qwen3.8's stability rows rest on few distinct answers.
- **vLLM's batch invariance depends on its FP8 kernel.** With DeepGEMM, its default kernel on Gemma 4, the answers of two fresh servers matched for 57.2% of requests; with `VLLM_USE_DEEP_GEMM=0`, which selects its CUTLASS block-FP8 kernel, for all of them. Both arms' logs show invariance active (its batch-invariant kernels traced, and its sampling warning): the second commit's driver reads it into the manifest's `batch_invariant_active`, and the earlier hosts' vLLM manifests have it filled in from their logs by the same rule.
- **No multi-turn cell.** One ran on `p2`, at 24 llm-mini-infer checkpoint slots for 48 conversations: a pressure at which its two arms could not differ. It is not published.
- **SGLang's scene answers are shorter** than the other engines' for the same requests (A1 c=1: 157 tokens against 228 and 192), and with deterministic inference much shorter (about 25 tokens): its scene rows, its stability in that mode and its cost of invariance compare different outputs. **With deterministic inference on Gemma 4, SGLang gave 496–498 of the 500 scene requests one and the same answer** (3 and 5 distinct answers in its two passes, against 283–289 in its default mode, 416 for llm-mini-infer and 405 for vLLM with CUTLASS): its answers stop depending on the image, so its 99.2% identical is not a reproducibility result. The stability tables give each pass's distinct answers and the count of its most common answer. In family I, vLLM's invariant arm answered scene requests at more length than its default (235 tokens against 196 on average) and SGLang's at much less (26 against 163): the scene ratios of the cost of invariance compare different outputs, the chat ratios (`ignore_eos`, 256 tokens each) the same work.
- **One request failed** in vLLM's Gemma 4 rate search, at 5.27/s, more than its saturation rate: the connection closed without an answer (`ServerDisconnectedError`); that probe failed the bound on its latency too.
- **The 3% clock rule:** loads at 64 or 16 in flight run at the 600 W power limit, whose clock sits up to 5.4% below a host's lighter loads (`summary.md`, the clock check). The GPU controls show `p2`'s clock steady within 2% over its run; `p3`'s end control (after Qwen3.8's A1 of llm-mini-infer and vLLM) ran 2.6% below its start in bf16 and 2.5% in fp8, with the bf16 clock at 2,145 against 2,220 MHz, all at the power limit. Against `p2`'s A1 of the same arms (in this folder), llm-mini-infer's rows on `p3` differ by at most 1.3% (TPOT, e2e p50, req/s, tok/s), vLLM's by at most 3.9% but at scene c=16, where `p3` gave 9.5% lower TPOT p50 and 6.1% more tokens per second. No load was rerun.
- **The vendor pods** ran each engine with its image's whole environment under the arm's variables (the manifests' `source`); their manifests list the generic variable names only.
- **Validity reports** keep each request's verdict, finish reason and tokens, without the answers' texts: the benign corpus asks for dates, emails, URIs and ids. vLLM's attention backend in its manifests is read from its startup log (on `p1` and `p2` at publication, where the measured commit's pattern missed it).
- **Scope:** one GPU and power limit; synthetic workloads; no MoE, no tensor parallelism; other drafters not compared. Batch invariance in vLLM and SGLang is documented as beta or tested on other models: their numbers describe this configuration. Results move with versions.

## Files

`runs/<host>/<model>/<family>/<unit>/`: the run.py reports (`<workload>-c<N>.json`, `stability.json`, `find-rate.json`, each with its loads and answer digests), `startup.json`, `smoke.json`, `validity.json` and `grammar-cost.json`; `runs/<host>/<model>/C/<arm>-compare.txt`: `bench/load/compare.py`'s output for the two passes. `manifests/<host>/<model>/<family>/<unit>.json`: each unit's arm, command, environment variable names, versions, resolved settings, smoke checks, start, loads with their clock and power (and, at the second commit, each load's client settings), host and status. `control/<host>-<label>.json`, `bounds/`, `freeze-diff.txt`, `vendor-images.json`, `commands.sh`.

llm-mini-infer's structured-output caps are in `llm_mini_infer/grammar/bounds.py`: a schema over a cap is refused with a 400 before it reaches the grammar compiler; the refusal tests cite guidance-ai/llguidance #436 to #444. `grammar-cost.json` (and `summary.md`) give the compile cost at those caps for each model's tokenizer.

## Running it again

On a host with this GPU, from the GPU tests' image of a commit (`tests/gpu-image.Dockerfile`, on the release image `ghcr.io/deftinfer/llm-mini-infer:<release>`): install vLLM v0.33.0 and SGLang v0.5.23 into the venvs `bench/engines/arms.py` names (`BIN`) at `freeze-diff.txt`'s versions (vLLM's image pins `nvidia-nccl-cu13` past torch's own pin), download the two models into the Hugging Face cache it names (`HF_HOME`), then run `commands.sh` from the repository's root. The release's kernels are the measured image's when `KERNELS_SHA256` in `deploy/Dockerfile` is the same at the release as at the measured commit: the image build refuses any other bytes.
